# ffprobe媒体信息持久化

作者：gitbose；版本：1.1

独立的 MoviePilot V2 插件，不修改“ffprobe命名补充”。优先复用命名阶段取得的 ffprobe 数据，在整理成功后将 Emby MediaInfo JSON 写入最终媒体目录。缓存写入池最多 32 并发，主动提取、筛选、异常大小记录、失败记录及延迟清理仍按已有配置执行。

## 本次 HDR 修复

- HDR10：根据 `smpte2084` 填写 `ExtendedVideoType=Hdr10` 和 `ExtendedVideoSubType=Hdr10`，不再只设置 Emby 不会直接采纳的 `VideoRange` 字符串
- HLG：根据 `arib-std-b67` 填写两个 `HyperLogGamma` 字段
- 杜比视界：根据 `dv_profile` 与 `dv_bl_signal_compatibility_id` 保留子类型，如 Profile 5.0、7.6、8.1；不把 `dv_level` 当作 Profile
- 不根据文件名、10bit 或 BT.2020 单独猜测 HDR；资料不足时保留未知结果

以上转换作用于复用缓存和主动提取，不增加额外源请求，不修改上游缓存中的原始数据。

## HDR 帧级增强识别

配置页新增此开关，默认关闭。常规流级 JSON 没有 HDR10+ 动态元数据，或色彩标记存在歧义时，纯字段转换无法补齐这些信息。

开启后，仅对 PQ、`bt2020-10`、`bt2020-12` 候选视频追加限量帧探测。已有可靠 HLG、杜比视界、HDR10+ 标记的流，以及普通 SDR，不追加此探测。每次限量读取前 60 个视频包；独立后台并发数为主动提取并发数与 3 的较小值，超时沿用主动提取超时配置。

基础 JSON 先落盘，增强不阻塞 MP 整理或 32 线程基础写入池。增强成功后原子更新该 JSON；超时、网络错误或缺少证据时保留基础 JSON。文件被重新整理、JSON 被其他任务改写、插件停用或重载时，不使用旧增强任务覆盖变化后的结果。多帧色彩数据相互矛盾时不推断。

增强需要 MP 容器里的 ffprobe 支持相应解码器和帧级元数据，且网盘链接在超时内可访问。限量探测不保证发现只在更后位置出现的动态元数据。新增增强任务未单独做断电续跑持久化，重启后已生成的基础 JSON 仍保留。

## 安装及验证

1. 将 `上传` 目录内的全部内容上传到仓库根目录，保留 `package.v2.json`、插件目录、前端源码与完整 `dist` 编译产物；不要只上传 Python 文件
2. 让 MP 拉取新插件文件并重载，浏览器刷新前端缓存；本次版本保持 1.1，同版本如无法拉取，应先备份插件配置和记录，再按 MP 支持的方式重新安装
3. 普通 HDR10、常规 HLG、杜比视界转换默认生效；若要识别样本中的《好兆头》HDR10+ 和《反叛女人》流级/帧级 HLG 冲突，开启“HDR 帧级增强识别”
4. 已有旧 JSON 不会自动批量改写，且“覆盖同名 JSON”关闭时仍保留已有文件；需要更新的条目应开启覆盖后重新生成
5. Emby 已入库的信息不会仅因更新插件立即变化。先用单条媒体重新生成 JSON；增强开启时等待“已更新 HDR 帧级信息”日志，再让神医助手/Emby 重新读取媒体信息，并核对 Hills 显示

本次没有修改 NAS 原文件或 Emby 数据库，也没有自动推送 GitHub。已通过 29 项回归测试、19 份真实源探测结果转换及 Emby 4.8.0.80 SDK 模型反序列化核验，并重新实时探测了 3 个帧级案例。尚未进行线上 Emby 导入/Hills 显示验证。
